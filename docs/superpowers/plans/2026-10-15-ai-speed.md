# AI speed and truncation — plan

> **For agentic workers:** each step has its own branch, tests written first, and a "What landed" entry. This file is gitignored; commit it with `git add -f`. Merge with `--no-ff`; never push.

**Report (maintainer, 2026-10-15):** the AI features are too slow; analysing a book gets cut off (「AI 回覆被截斷」) or takes about 100 requests.

## Root causes (found in code, 2026-10-15)

1. **Every feature but 人物 extraction asked DeepSeek for nothing, and DeepSeek thinks at high by default** (`OpenAICompatibleProvider`: `reasoningEffort ?? "high"`).
   - `max_tokens` covers the thinking as well as the answer.
   - Our default was 16,384, while DeepSeek allows 384K (https://api-docs.deepseek.com/quick_start/pricing, https://api-docs.deepseek.com/guides/thinking_mode).
   - High thinking on long text spent the allowance before the answer was written: truncated, and slow.
   - Thinking was also sent only for four listed model ids. Any other DeepSeek model got the server's default, high.
2. **Small batches:**
   - 全書摘要 sends 12,000 UTF-16 and at most 8 chapters per request. A 1M-character novel is about 85 requests, one after another.
   - 人物 extraction sends 1,200 characters per request, capped at 100 requests per run.
   - 整章翻譯 sends 2,000 characters per request, one after another.

## Maintainer's decisions (2026-10-15, by option, all the recommended ones)

1. **Thinking:**
   - Mechanical work runs with thinking off: 翻譯, 查詞, 書架整理, chapter digests, 人物 extraction, and the connection probe.
   - 問書 and the summaries made from digests think at high.
2. **Bigger batches, three at a time:**
   - 全書摘要: 12K → 48K per request, 8 → 32 chapters.
   - 人物: 1.2K → 4K per unit.
   - 翻譯: 2K → 6K.
   - Up to three requests run at once.
3. **Output allowance:** 64K for a service known to allow it (DeepSeek); 16K kept for the rest, because some services refuse a larger value.

## Steps

- **1 — thinking and allowance** (`ai/speed-1-reasoning`).
  - `LLMReasoningEffort.off`.
  - The DeepSeek endpoint is sent each feature's choice for every model id.
  - `max_tokens` is at least 65,536 on DeepSeek.
  - Each request builder states its effort.
- **2 — 全書摘要 batches and concurrency.**
  - `batchUTF16` 48,000; `batchParts` 32.
  - Digest batches run three at a time.
  - Each batch is still committed as it finishes, and a failure stops the run as before.
- **3 — 整章翻譯 concurrency.**
  - Revised by the maintainer, 2026-10-15: batches stay at 2,000, three at a time, the reader's position first.
  - A translation is as long as its source, so a 6,000-character batch would make a typical chapter one request: no faster, and nothing shown until it was done.
- **4 — 人物 units:**
  - `AIMemoryBudget.unitCharacters` 4,000.
  - Units stay sequential, because each reads the records before it.
  - Existing jobs keep the budget they were planned with.
- **Measurement:** `AIDiagnostics` already records each request's elapsed ms and its prompt, completion and reasoning tokens.
  - Real numbers need the reader's own key, which these tests cannot use.
  - The tests pin request counts (before/after) for a fixed book.

## What landed

### Step 1 (branch `ai/speed-1-reasoning`)

- `LLMReasoningEffort.off`.
- `OpenAICompatibleProvider` changes for the DeepSeek host:
  - `thinking` is disabled for `.off`, and enabled with the effort otherwise;
  - `max_tokens` is `max(request, 65_536)` (`deepSeekOutputTokens`);
  - other hosts are unchanged.
- Thinking off: translation, word lookup, bookshelf organizer, chapter digests (`AIBookSummaryPrompt.digestEffort`), 人物 extraction (was `.low`), and the connection probe.
- Thinking at high: 問書 (every agentic step, since any step may finish with the answer; `AIQuestionEvidence.reasoningEffort`) and the summary reduce steps.
- Tests:
  - `AIReasoningBudgetTests` (7, new);
  - `AIProviderTests` updated for the 64K DeepSeek allowance;
  - an `AIPhase3CharacterMemoryTests` assertion;
  - 7 suites green (86 tests, then the provider pair 26/26, then memory 26/26).

### Step 2 (branch `ai/speed-2-summary-batches`)

- `AIBookSummaryPlanner.batchUTF16` 12,000 → 48,000 and `batchParts` 8 → 32.
  - 100 chapters of 4,000 characters: 34 → 9 digest requests.
  - 200 short chapters: 25 → 7.
  - Stored digests are per chapter, so none is redone.
- `AIBookSummaryService`: chapter digests run `concurrentDigests` = 3 at a time, in a task group isolated to the main actor.
  - Each call is reserved (and saved) before it is sent. Each batch is parsed and saved as it returns.
  - The first failure stops the run. Batches still in flight are cancelled; their reserved calls stay counted.
  - Running out of confirmed calls lets the in-flight batches finish and keeps them.
  - Volume and book reduce calls stay sequential (few calls; they think at high).
- Tests: `AIBookSummaryTests` 14/14, three of them new:
  - batch sizes and request counts;
  - the first three digest requests are held until all three arrive, and the most in flight is 3;
  - a failing fourth digest stops the run and keeps the finished batches.

### Step 3 (branch `ai/speed-3-translation`)

- `AIChapterTranslationService.concurrentBatches` = 3. The batches go out in `pending`'s order (on screen first).
- Each batch is parsed, saved and announced (`updates`) as it returns. Progress counts finished batches. The first failure stops the run.
- `batchCharacters` stays 2,000 (maintainer).
- Tests: `AIChapterTranslationTests` 7/7, with a new one: 8 paragraphs in 4 batches, the first three held until all three arrive, the most in flight 3, the reading paragraph's batch sent first, and every paragraph stored.
