# 渲染相似度的量法

[首頁](README.md) · [目標](GOAL.md) · [已知差距](GAPS.md)

這份文件定義「和 WebView 幾成像」這個數字。量法、腳本與測試由 `scripts/fidelity/oracle.lock` 鎖住雜湊：這些檔案一改，`measure.sh` 就不量，直到照下面「改量法」重新上鎖。量別的程式樹時用主工作目錄的副本來評分，被量的改動不會同時改到評分方式。

## 比的是什麼

| | 我們這邊 | 對照組 |
|---|---|---|
| 渲染者 | 正式的捲動路徑：`CoreTextScrollEngine` ＋ `BrowserLayoutPageEngine(.browserAuto)`。被能力判斷拒絕的章節照常回退 Legacy，量到的就是讀者看到的 | 同一台模擬器上的 `WKWebView`，直接載入 EPUB 解壓後的原始 XHTML 與它自己的 CSS、字型、圖片 |
| 畫面 | 390 × 800pt，左右邊距 12pt → 內容寬 366pt；直排書是整寬 390pt、欄高 776pt | 同尺寸的 web view，`width=device-width` |
| 閱讀設定 | 字級 17、行高 1.5，段距／字距／行距加成為 0，不加粗、不指定字型、黑字白底 | 見下一節 |
| 語言環境 | 繁體中文（台灣），由 `measure.sh` 用 `-testLanguage zh-Hant -testRegion TW` 指定，和模擬器自己的語言設定無關 | 同一個行程的語言（`navigator.language` 是 `zh-TW`） |

用捲動而不是翻頁，是因為換頁位置是閱讀器自己的事，WebView 沒有對應物；整章排成一條連續的頁面後，兩邊才是同一件事。

語言環境要固定，是因為兩邊的字型替代順序和標點寬度都跟著系統語言走。同一章在英文介面和中文介面的模擬器上，不固定語言時換行位置會不同（全職高手有一章差 0.7 分）；固定之後，兩台模擬器量同樣的 6 章，每一章分數完全相同。對照組的快取鍵含語言，擷取時也會核對測試行程和 WebView 用的是同一種語言，不一致就讓量測失敗，不會默默量下去。

### 給對照組的樣式只有閱讀器自己的預設

```css
html{font-size:17px;line-height:1.5;text-align:justify;font-family:"PingFang SC";
     -webkit-text-size-adjust:100%;text-size-adjust:100%}
img{max-width:100%;height:auto}svg,video{max-width:100%}
```

這段插在 `<head>` 最前面，優先序最低，書自己的任何規則都能蓋過它。每一條都對應引擎裡一個刻意的閱讀器預設，不是為了讓分數好看：

| 規則 | 引擎裡的出處 |
|---|---|
| 字級、行高倍數、預設兩端對齊 | `ComputedStyleTreeBuilder.buildTree` 把閱讀設定當成根節點繼承值；`makeBrowserConfig` 的 `defaultTextAlignment: .justified` |
| 預設字型 PingFang SC | `InlineLayout.resolvedFont`：讀者與書都沒指定字型時從 `PingFangSC-Regular` 開始 |
| 圖片不超出容器、等比縮 | `BlockLayout.resolveReplacedSize` 的容器寬度上限（所有閱讀系統都這樣做） |
| 關掉 iOS 文字自動放大 | 引擎沒有這個行為 |

除此之外一律以 WebKit 為準：標題字級、段落 margin、清單縮排、`body` 的 8px margin 等 UA 預設，引擎和 WebKit 不一樣就是扣分。書裡的 script 不執行（`allowsContentJavaScript = false`），和閱讀器一致。

## 怎麼對齊

兩邊都輸出同一種資料：每一小段文字（同一行、同一種樣式）的字元範圍、位置、字級、粗斜體、顏色；每張圖的位置與大小；以及整章畫面切成 4pt 小格後每格的平均色與「最多像素共用的顏色」。

1. **文字對齊。** 去掉空白與控制字元後，把兩邊的文字流逐字配對；中間有一邊多出或缺少一段時，從下一個共同的 6 字序列接回去。同一個字的不同呈現形式算同一個字：直排用的標點（︐、﹁）和一般標點（，、「）、全形和半形，都先折成同一個再比。換哪種字形是排版的選擇，位置仍然照比。
2. **段落。** 對照組裡同一個區塊容器的連續文字算一段；同一批字在我們這邊落在哪些行，就是我們的同一段。
3. **行。** 一小段文字和前一小段在跨行方向重疊、沿行方向相鄰，就算同一行。直排時兩個軸對調，跨行方向從右邊量起。

因為是用「同一個字」對齊，前面多換一行只影響那一段，不會讓後面整章錯位。

## 排版分（佔一半）

每一段、每張圖各自計分，再依它在對照組裡的視覺份量加權。文字＝每行的字級加總。圖片＝同樣面積的文字會有的份量：和文字欄一樣寬的圖是高度 × 0.66（最多算一個畫面高），比較窄的圖按寬度比例縮小，所以一個字大小的行內小圖只佔很小的份量。

**一段文字**的分數 ＝ 配對到的字元比例 × 下列四項：

| 項目 | 權重 | 內容 |
|---|---:|---|
| 行 | 0.30 | 一半看行數是否相同；一半看每個換行點是否相同（差 1 個字得 0.6、差 2 個字得 0.3、更多得 0） |
| 水平 | 0.25 | 文字欄的起點、文字欄的寬度、首行相對於文字欄的縮排，各自比較；單行段落改比起點與置中位置 |
| 垂直 | 0.25 | 行與行的間距；和上一段（或上一張圖）的距離 |
| 字 | 0.20 | 字級 0.60、粗體 0.15、斜體 0.10、顏色 0.15，逐字比 |

位置類的比較都有容許值（1.5–2pt 內滿分），再線性遞減到 0：欄起點差到行寬的 12% 歸零，欄寬差到 20% 歸零，縮排差到 1em 歸零，行距差到 30% 歸零。

**一張圖**：大小 0.50、左右位置 0.25、和上一項的距離 0.25；我們這邊沒有這張圖就是 0 分。兩邊的圖用檔名依序配對；我們這邊說不出檔名的圖（例如整頁封面）照順序配。

另外兩條：

- 我們畫了對照組沒有的字（例如隱藏文字被畫出來），整章排版分最多扣三成。
- 對照組是直排而我們排成橫排（或相反），整章只保留三成分數。上面的比較都在「沿行／跨行」的座標裡做，方向錯了本來會看不出來，所以單獨處理。只有圖、沒有字的頁面（封面）沒有方向可言，不套這一條，圖直接照它在頁面上的位置比。

## 畫面分（佔一半，但只在有東西可比時）

文字的位置與樣式已經在排版分裡算過，畫面分只看**畫上去的東西**：背景色、邊框、圖片、裝飾。

1. 以配對到的段落與圖片的上下緣為錨點，把我們的畫面沿捲動方向分段拉伸，讓同一段落落在同一排格子上。
2. 逐格比顏色。有文字的格子比「紙的顏色」（最多像素共用的那個顏色）；如果那格幾乎被字蓋滿，就不算。沒有文字的格子比平均色。
3. 兩邊都是頁面底色的格子不計；其餘的格子，色差 8 以內算相同，到 64 算完全不同。

畫面分＝有內容的格子的平均相似度。這些格子佔全章不到 3% 時（純文字章節），畫面分的權重按比例降低；沒有任何可比的格子時，整章只看排版分。

## 分數

```
章節分 = 100 × (0.5 × 排版 + w × 畫面) / (0.5 + w)      w = 0.5 × min(1, 有內容的格子佔比 / 3%)
書的分數 = 它被量到的章節的平均
```

**一本書過關**＝書的分數 ≥ 80，而且：

- 閱讀器這邊沒有任何一章擷取失敗（排版丟錯、畫不出來都算失敗，那是引擎的問題）；
- 抽到的章節至少有一半量得到。

對照組（WebView）自己畫不出來的章節不算在書的分數裡，也不會讓書不過——那一章沒有標準答案可比，不是引擎的錯——但報告的「Not measured」會列出來。一本書超過一半的章節都沒有對照組時，這本書視為「沒量到」，不算過，要人來看。

低於 60 的章節另外列成警示。

### 抽哪些章節

章節清單用閱讀器自己的 `PublicationSession.chapters`。每本書：

- **dev**：釘選章節（`corpus.json` 的 `pinned`，來自歷史抽查清單與已知問題章）＋ 等距 10 章，頭尾都含。
- **holdout**：dev 兩兩之間的中點 6 章，不和 dev 重疊。

平常對著 dev 找問題、改引擎；holdout 只在驗收時量，用來抓「只對看過的章節有效」的修法。章數不到 10 的書全部進 dev。

## 兩次量測怎麼比

`fidelity.py compare --run <新> --base <舊>` 只比兩次都量到的章節，章節屬於 dev 還是 holdout 以舊的那次為準。

兩次都走舊引擎的章節不算進去。切片碰不到舊引擎（gate 擋著），而舊引擎的章節每次量會小幅漂移：2026-10-01 把整份基線在同一台模擬器上重量一次，走新引擎的 177 章每一章分數都完全相同，走舊引擎的 72 章最多差 2.8 分（hongwu:43）。把它們算進去，漂移就會被當成進步或退步。

| 結果 | 條件 |
|---|---|
| `PASS` | 有進步，而且沒有任何一條失敗 |
| `NO PROGRESS` | 沒有失敗，但也沒有進步 |
| `FAIL` | 下面任何一條成立 |

- **進步**：某本書（dev＋holdout 合計）上升 ≥ 0.3；或某個回退原因從那本書消失，而且原本因為它回退的章節沒有一章下降超過 0.05。
- **失敗**：某本書的 dev 章節下降超過 0.5；某本書的 holdout 章節下降超過 1.0；走新引擎的章節數變少；原本量得到的章節現在量不到；擷取沒跑完；兩次用的量法版本或對照組不同；加了 `--full` 卻沒有把舊的那次的章節全部重量。

門檻寫在 `fidelity.py` 最上面的常數裡，和其他計分常數一樣屬於量法。

## 它看不到的東西

這些是量法的限制，讀分數時要記得：

| 限制 | 影響 |
|---|---|
| 不量換頁 | 翻頁模式特有的問題（跨頁裝飾、圖被推到下一頁的留白）不在分數裡 |
| Legacy 把表格畫成一張圖 | 表格裡的字量不到位置，算成缺字；圖本身仍會進畫面分 |
| CSS 產生的內容（`::before`、清單符號）不在文字流裡 | 只透過畫面分反映 |
| 不比對實際用了哪個字型 | 字型不同只會透過換行、行距、字寬間接顯現 |
| 注音（ruby）標註 | 只透過畫面分反映；base 文字正常比較 |
| 淺色細邊框（和底色色差 < 8） | 看不到 |
| Legacy 橫排的行寬 | 由實際畫出來的墨跡反推，精度約 1pt |
| Legacy 直排的行內批註（`span.small`） | 舊引擎把批註畫在正文之外的另一條路徑上。擷取時照那條路徑的規則重算每個字和小圖的位置，再把批註的字接回正文的文字流；那條路徑的規則改了，這裡要跟著改 |
| Legacy 在一塊裡只有一張圖、又排不進那一塊時什麼都不畫 | 量測用的設定（段距 0）下，章末的圖和沒被認成封面頁的封面會遇到；分數照實算成缺圖 |
| 捲動宿主畫的整頁背景（`BrowserChapterBackdropView`、`CoreTextChunkBackdropView`） | 擷取時照宿主的規則重畫一次，不是宿主本身；宿主的規則改了，這裡要跟著改 |
| 對照組 XHTML 解析失敗、或 WebView 在時限內沒有回應 | 該章列為「未量測」，不進書的分數（規則見上面「分數」） |
| 書裡指定了載不到的字型（例如寫死成別台裝置的路徑） | WebView 等字型最多 8 秒、等圖片最多 15 秒，時間到就照當下的樣子量；報告的「Reference caveats」會列出哪幾章 |

## 自我檢查

`python3 scripts/fidelity/test_fidelity.py` 是量法自己的測試，多數是反向對照：故意做出已知的缺陷，分數必須下降，而且要指對原因。

- 同一份渲染對自己必須是 100 分（合成資料與真實擷取都驗過）。
- 每行少排一個字、沒有縮排、行高 1.2 對 1.5、字級 14 對 17、顏色與粗體錯、少一段、多一段、少一張圖、圖縮一半、少一塊背景、頁面底色不同、直排被排成橫排：各自有測試。

改引擎之前如果懷疑分數不合理，先對照 `runs/<run>/index.html` 的並排圖；分數和眼睛看到的明顯不符，是量法的問題，停下來回報，不要去湊分數。

## 改量法

只有人可以改，而且不和引擎修改放在同一個 commit：

1. 改 `scripts/fidelity/` 或 `RenderFidelityOracleTests.swift`，`SCORER_VERSION` 或 `extractorVersion` 加一。對照組的快取鍵（`refKey`）只看設定檔、注入樣式、和擷取腳本的內容；改到「什麼時候算載入完成」或捲動、截圖的做法時，腳本內容沒變也要手動把 `extractorVersion` 加一，舊的對照組才會重擷取。
2. `python3 scripts/fidelity/test_fidelity.py` 全過。
3. `python3 scripts/fidelity/fidelity.py lock --write` 重錄雜湊。
4. 重跑基線，把新舊分數差異寫進 `reports/`，因為之後的分數和之前的不能直接比。

只改說明文字（文件、註解）或拆掉不參與評分的指令，不會改變分數的意義：`SCORER_VERSION` 不加、基線不重跑，只做第 2、3 步（2026-10-07 拆掉 loop 的 `gate` 指令就是這樣做的）。
